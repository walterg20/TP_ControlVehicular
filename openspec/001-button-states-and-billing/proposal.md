# Proposal: Button States and Billing Fixes

## 1. Problem Statement
**UI State Issues:**
Currently, in the Service Orders screen (`CtlOrdenServicio.xaml`), the "Comp. Pago" (Payment Receipt) and "Pagar" (Pay) buttons are always enabled. Although there is a code-behind check that prevents printing a receipt for an unpaid order, it shows a popup warning rather than proactively disabling the button. Users can click "Pagar" on orders that are unfinished ("Pendiente", "En Proceso", "Cancelado") or already paid ("Pagado").

**Billing & Invoice Issues:**
1. **Invoice Number Generation:** `BillingService.GenerarFactura` generates invoice numbers using `(int)(DateTime.Now.Ticks % int.MaxValue)`. This is highly susceptible to collisions and does not guarantee sequential or unique numbers.
2. **Duplicate Invoices:** `GenerarFactura` does not check if an invoice already exists for a given service order, potentially allowing multiple invoices to be created for the same order.
3. **Double Payment Risk:** `RegistrarPago` checks the current balance but lacks concurrency controls. Furthermore, since the UI allows opening the payment screen multiple times, a user might accidentally pay the same order twice if multiple invoices are generated or concurrent requests are made.

## 2. Proposed Solution

### UI Improvements
- Convert the auto-implemented `OrdenSeleccionada` property in `OrdenServicioViewModel` into a full property that raises `PropertyChanged` for itself and dependent properties: `PuedePagar` and `PuedeVerComprobantePago`.
- Bind the `IsEnabled` attribute of the "Pagar" and "Comp. Pago" buttons in `CtlOrdenServicio.xaml` to these new properties.
- **Rules:**
  - `PuedePagar`: True only if `OrdenSeleccionada.Estado == "Completado"`.
  - `PuedeVerComprobantePago`: True only if `OrdenSeleccionada.Estado == "Pagado"`.

### Billing Improvements
- **Invoice Generation:** Modify `BillingService.GenerarFactura` to first check if an invoice already exists for the `registroServicioId`. If it does, return the existing invoice instead of creating a new one.
- **Database Auto-increment:** Ensure the invoice number (`Numero`) is generated by the database at INSERT time (e.g., using IDENTITY) instead of calculating it in code, to prevent race conditions.
- **Database Unique Constraint:** Add a UNIQUE constraint on the `RegistroServicioId` column in the `Factura` table to strictly prevent double billing at the DB level.
- **Concurrency/Validation:** Ensure `RegistrarPago` remains robust. By fixing the UI to prevent opening the payment screen for non-"Completado" orders, the risk of double payment is significantly mitigated. The new DB constraints act as the ultimate safeguard.

## 3. Impact
- **User Experience:** Proactive disabling of buttons prevents invalid actions and unnecessary error popups.
- **Data Integrity:** Invoices will have unique, consecutive numbers without risk of collisions. Duplicate invoices and double payments will be prevented.
